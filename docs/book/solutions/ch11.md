# Solutions, chapter 11

## Review questions

1. In Win32 the check state is inside the control and you query it with `BM_GETCHECK`. Here it is your own `bool`, passed by reference. To disable a group you cannot send `EnableWindow` to handles, because there are none: you wrap the calls in `beginDisabled()` and `endDisabled()`, which dims everything drawn between them and makes `clickBehavior` return false.
2. A closed menu has no items on screen, so building them would be wasted work, and worse, `menuItem` would allocate rows and react to the mouse for a popup nobody sees. Returning `false` means your item calls and their side effects do not run. If it always returned `true`, every menu item would be tested for clicks every frame and your `if (menuItem(...))` blocks could fire while the menu is closed.
3. The pointer still rests on the File header. Each frame the header wins the hover test, and without a check for pointer movement it re-opens File right after the Right arrow switched to View. The flag is `input_.moved`: hover switching only happens when the pointer actually moved since the last frame.
4. The scrim only changes how the earlier widgets *look*; they have already run their hit tests by the time the dialog is drawn. Drawing last makes the dialog appear on top. `blockOutside_` makes the earlier widgets stop reacting in the following frames, because `hovered()` and `registerFocusable()` return false for them. Without it the user could click through the dim layer, or Tab to a button behind the dialog and press Enter.
5. In frame N+1. `blockOutside_` is set at the start of a frame from `modalOpenNow_` of the previous one, because the widgets behind the dialog run before the dialog is called and cannot know it exists. One frame of lag is not noticeable, and after input `drawFrame` runs two passes anyway, so the second pass of the same event already blocks them.
6. The ids are assigned by a counter in traversal order. If a collapsed folder does not add the size of its hidden subtree, every node after it gets a smaller id than when it was open. The stored `selectedNode` then points to a different node, and the selection jumps to whatever now has that number. `testTree` collapses a folder and checks that `selectedNode` is unchanged.
7. A program that sleeps in `waitEvent(-1)` is only woken by input, and a resting pointer sends no events, so the tooltip would never appear. `tooltip()` stores the remaining time in `tipWakeMs_`, and `nextWakeupMs()` returns it (or the caret blink time if that is sooner). The event loop passes it to `waitEvent` as the timeout.
8. The popup rectangle is stored in `popupRect_` while it is built, and saved at the next frame start as `prevPopupRect_` with `prevPopupActive_`. `hovered()` returns false for points inside either rectangle. The list box ran before the popup existed this frame, so it relies on the previous frame's rectangle, which is the same place.

## Exercises

**Ex 11.1** A sketch that fits the existing structure:

```cpp
bool Context::menuCommand(std::string_view label, Key key, bool ctrl, bool* checked, bool enabled) {
    std::string accel = ctrl ? "Ctrl+" : "";
    accel += static_cast<char>(std::toupper(static_cast<int>(key)));   // letters: Key::A == 'a'
    bool fired = menuItem(label, accel, checked, enabled);
    if (enabled && shortcut(key, ctrl)) {
        fired = true;
        if (checked) *checked = !*checked;
    }
    return fired;
}
```

The problem is that `shortcut` only runs when the menu is open, because `menuItem` is only called then. So the key must be handled even when the menu is closed. Keep a registry: `menuCommand` pushes `{key, ctrl, label}` into a list while the menu is open, and a table built once at startup would be better. A small data driven solution: define `struct Command { std::string label; Key key; bool ctrl; std::function<void()> run; }`, and have both the menu and a `for (auto& c : commands) if (ui.shortcut(c.key, c.ctrl)) c.run();` loop use the same array.

**Ex 11.2** The tree needs focus (`registerFocusable` with an id for the whole tree), a way to know the node above and below the selected one, and the open state of the selected node. Today the application owns the selection (`selectedNode`) and the toolkit owns the open flags (`treeOpen_`). One approach is to make `treeNode` take a `bool* selectedOut` and give the tree a `beginTree(id)` that handles the keys: Up and Down change `selectedIndex_` (an index in the visible rows, counted while drawing), Left sets the open flag of the selected node to false, Right to true. The rows drawn compare their running index with `selectedIndex_`. The visible row count is only known after drawing, so Down must clamp the following frame, the same one frame lag as everywhere else.

**Ex 11.3** Use `button` with an id and the glyph as text (`"⚙##gear"`), pass `width(32)` first, and call `tooltip` directly after it:

```cpp
ui.beginRow();
for (const auto& t : tools) {
    ui.width(32);
    if (ui.button(t.glyph + "##" + t.name)) t.run();
    ui.tooltip(t.name);
}
ui.endRow();
```

Check that the font has the glyph, otherwise Pango substitutes another one and the size changes.

**Ex 11.4** Keep a `std::string buffer` per spin box in a map keyed by id, and a flag whether the field has focus. While it has focus, edit the buffer with the text field code (reuse the same function by extracting it from `textField`). After every change, try to parse the buffer; if it parses, update `value`. When focus leaves, replace the buffer with `std::to_string(value)` so a half typed "-" or the empty string is repaired. While focused with an invalid buffer, keep showing the buffer, not the value, or the user could never type a minus sign.

**Ex 11.5** `openMenu_` becomes a stack (`std::vector<Id>`) of the open chain: bar menu, submenu, sub-submenu. A `beginSubMenu(label)` row works like a menu header: while hovered for 250 ms (a timer like the tooltip, with a wake up request) it pushes its id and builds a popup at `row.right(), row.y`. Closing: when the pointer is outside every popup in the chain and not on the row that owns the deepest one, pop levels. The popup blocking rectangle must become a list or the union of all popup rectangles.

**Ex 11.6** Sketch:

```cpp
if (ui.beginModal("Rename", renameOpen, 420)) {
    ui.textField("newname", name);
    const bool enter = ui.shortcut(ww::Key::Enter);
    ui.beginRow();
    if (ui.button("OK", true) || enter) { rename(name); renameOpen = false; }
    if (ui.button("Cancel")) renameOpen = false;
    ui.endRow();
    ui.endModal();
}
```

Initial focus: when `beginModal` sees the dialog appear (`!blockOutside_`) it clears focus. You want the text field to have it. Add a `bool setFocusNext()` or let `textField` take a `focusOnAppear` argument that sets `focusId_ = id` the first frame it is drawn. Note that `shortcut(Enter)` does not run if the text field has focus and consumed the key first, so call `shortcut` before `textField`, or give the field a way to report "Enter pressed".

**Ex 11.7** The first time the File menu opens, `menuSizes_` has no entry, so the popup is drawn with the default width and zero height on the first pass, then `endMenuPopup` stores the real size and sets `needsRedraw_`, so a third pass is needed (two for input, one more for the settle, up to four). The second time, the size is remembered and the popup is correct on the first pass, so only the usual two passes run. Instrument `drawFrame` with a counter and print it.

**Ex 11.8** State per list view: column widths (vector of floats, so that resizing persists), the sort column and direction, the vertical scroll offset, and the id of the column being dragged. Rows from a table of strings: `std::vector<std::vector<std::string>>`. A header click sorts a vector of row indices rather than the table, so the application's data stays untouched, and the function returns the selected row index in the original table. Draw only visible rows (the scroll offset divided by the row height), as `listBox` does. A callback version (`std::function<void(Rect, int row, int col)>`) lets a cell hold anything but needs the caller to do the text drawing and clipping.
