# Solutions, chapter 1

## Review questions

1. Under Ubuntu's X11 session: display server is Xorg, window manager is Mutter (or another WM), compositor is also usually Mutter. Under GNOME Wayland, Mutter is all three.
2. X11 lets any client query and read any window, so a screenshot tool just asks the server for the pixels. Wayland isolates clients: a client only holds its own buffers, so capturing the screen needs the compositor's cooperation (a portal or a special protocol) and usually a permission prompt.
3. KDE Wayland supports server side decorations (KWin draws the title bar). GNOME Wayland does not, so the client must draw its own.
4. Sleep when there is nothing to do, and draw only when something changed.
5. XWayland is an X server that runs as a Wayland client, so X11 programs work on a Wayland desktop. It lets you test your X11 code even if your login session is Wayland.

## Exercises

**Ex 1.1** Typical Wayland session output: `wayland :0 wayland-0`. `wayland` is the session type, `:0` is the XWayland display (X11 programs connect there), `wayland-0` is the compositor socket name. A pure X11 session prints `x11 :0` and an empty third value.

**Ex 1.2** `ls -l $XDG_RUNTIME_DIR/wayland-0`. It is a Unix domain socket (type `s` in the listing), usually under `/run/user/1000/`, owned by you with mode `srwxr-xr-x`. The directory itself is `0700`, which is what keeps other users out.

**Ex 1.3** The first lines give the server: version number, vendor string, release number, extensions list. The `screen #0` section gives dimensions, depth, visuals and root window.

**Ex 1.4** `xeyes` follows the pointer only while it is over an X11 (XWayland) window, because pointer coordinates are delivered to X clients only for X windows. Over a native Wayland window it stops tracking. This illustrates the isolation: X clients do not see global pointer state.
