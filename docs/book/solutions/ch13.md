# Solutions, chapter 13

## Review questions

1. The **platform half** (`Host`) feeds ImGui the input events, the display size and scale and the time, and carries the cursor shape and clipboard text out to the window. The **renderer half** (`SoftRenderer`) turns `ImDrawData` into pixels and services texture requests. Chapter 14 replaces the renderer half with an OpenGL one. The `Host` is unchanged.
2. The two libraries disagree on the sign. In `ww`, `ScrollEvent::dy > 0` means the content moves up (the user scrolls down), as chapter 4 defines it. In ImGui a positive wheel value scrolls up. `Host::handleEvent` negates both axes.
3. `DisplaySize` is 960 x 640 (logical units) and `DisplayFramebufferScale` is (2, 2). The framebuffer has 1920 x 1280 pixels. ImGui lays out in logical units and bakes glyphs at twice the density because of the scale.
4. The renderer's destructor walks `ImGui::GetPlatformIO().Textures` and frees its textures, which needs a live context. `Host`'s destructor destroys the context, so it must run last. Locals are destroyed in reverse order of declaration, so the `Host` is declared first.
5. It means "some regions of the texture contain new pixels, copy them". Copying only `tex->Updates` avoids touching the whole atlas (a megabyte or more) when a few glyphs were added. For a CPU copy it is a small saving, for a GPU upload it avoids a large transfer.
6. Edge functions give exact answers only if rounding cannot differ between two triangles that share an edge. Integers have no rounding. With floating point, a pixel centre on a shared edge could be claimed by both triangles or by neither, which would show as a double blended line or a gap.
7. The pixels on the diagonal would be drawn twice, once by each triangle, so a half transparent colour would be applied twice and the diagonal would look darker (or lighter). The top-left rule gives each such pixel to exactly one of the triangles.
8. It checks that the second triangle repeats the first and third index of the first (`ib[i+3] == ib[i]` and `ib[i+4] == ib[i+2]`), then that all four vertices have the same colour, that their positions are the corners of an axis aligned box, and that the UVs follow the same linear mapping. If any check fails, `drawQuad` returns `false` and the two triangles go through `drawTriangle`.
9. From geometry: ImGui adds thin strips of triangles around shapes with the outer vertices at alpha 0. A renderer preserves it by interpolating the vertex colour (including alpha) across the triangle and blending with alpha, which the general path does. A renderer that rounds alpha to 0 or 1 would lose the smooth edges.
10. Four times the pixels took four times as long, so the time is proportional to the number of pixels written, not to the number of triangles (which hardly changed). The first change is to reduce the work per pixel for the most common case: an opaque, solid rectangle should be a `std::fill` of a row. After that, band-parallel rendering or damage tracking.

## Exercises

**Ex 13.1** The buffer belongs to `main` (or an `App` struct), because only `main` sees the `ww::Event`s and the window. `Host::handleEvent` translates events into ImGui calls and returns, and it should not keep a history that only the UI needs. The gallery gets a pointer or reference to the buffer, in `gallery::State`, and prints it with `ImGui::TextUnformatted` inside a child window. Format events with `std::visit` and an overload set, as chapter 8 does for `Event`.

**Ex 13.2** Hash the bytes:

```cpp
uint64_t hash = 1469598103934665603ull;
for (const ImDrawList* list : data->CmdLists) {
    hash = fnv(hash, list->VtxBuffer.Data, list->VtxBuffer.Size * sizeof(ImDrawVert));
    hash = fnv(hash, list->IdxBuffer.Data, list->IdxBuffer.Size * sizeof(ImDrawIdx));
}
if (hash == lastHash) skip present()
```

The clip rectangles and texture ids belong in the hash too. While a text cursor blinks, the frame changes only twice a second, so almost all of the 60 frames per second during the 400 ms "busy" window after input are identical once the animations finish. The saving is most visible when nothing changes at all. Note that the CPU renderer still ran; to save the rendering you must hash before `render`.

**Ex 13.3** The draw command carries a texture id. The rasterizer only turns the id back into a `Texture*` and samples it, so it does not care whether the id came from the font atlas or from `createTexture`. The same would be true for a GL texture name. Implement `createTexture` with `new Texture`, fill `rgba` (the `0xAABBGGRR` order), return `reinterpret_cast<uintptr_t>`; `destroyTexture` deletes it. Keep a list of the textures you created so the destructor frees any left over.

**Ex 13.4** Bilinear sampling reads four texels around `(u * w - 0.5, v * h - 0.5)` and mixes them with the fractional parts:

```cpp
const float fx = u * w - 0.5f, fy = v * h - 0.5f;
const int x0 = std::clamp(int(std::floor(fx)), 0, w - 1), x1 = std::min(x0 + 1, w - 1);
const int y0 = std::clamp(int(std::floor(fy)), 0, h - 1), y1 = std::min(y0 + 1, h - 1);
const float tx = fx - std::floor(fx), ty = fy - std::floor(fy);
// mix the four texels per channel with weights (1-tx)(1-ty), tx(1-ty), (1-tx)ty, tx*ty
```

The scaled pattern becomes smooth instead of blocky. The text does not change at scale 1 and 2, because the glyph quads are placed on whole pixels and the atlas was baked at the display density: the sample points hit texel centres exactly, where both filters return the texel.

**Ex 13.5** In `drawQuad`, before the pixel loop: `if (!tex && channel(v0.col, 24) == 255) { const uint32_t pixel = 0xFF000000u | (r << 16) | (g << 8) | b; for (int y = ys; y < ye; ++y) std::fill(row + xs, row + xe, pixel); return true; }`. Most window backgrounds are opaque, but most pixels in this UI are *text and alpha blended rectangles*, so expect a modest gain, 10 to 25 percent. For the two band version, give each thread a clip range `[y0, y1)`: intersect it with every command's clip rectangle. The draw data is read only and each thread writes its own rows, so nothing is shared except read-only input and no locking is needed. The texture update step must run once, before the threads start.

**Ex 13.6** In `lib/platform/include/ww/window.hpp` add the three enum values. X11: `XCreateFontCursor(display, XC_sb_h_double_arrow)`, `XC_sb_v_double_arrow` and `XC_X_cursor` (there is no standard "not allowed" glyph in the cursor font; use the `X_cursor` or load `not-allowed` with Xcursor, `XcursorLibraryLoadCursor`). Wayland: `wl_cursor_theme_get_cursor(theme, "ew-resize")` and so on, with fallbacks such as `"sb_h_double_arrow"`, because theme names differ. Extend `Host::applyCursor` with the three `ImGuiMouseCursor_` values.

**Ex 13.7** Set `io.ConfigFlags |= ImGuiConfigFlags_NavEnableKeyboard` in the constructor. Tab, the arrows, Enter, Space and Escape already map. You will need `Key::Enter` for activation and also `ImGuiKey_KeypadEnter` is not produced by our platform layer, which only matters for numeric keypads. If Space does nothing on a focused button it means `Key::Space` is not forwarded: check `toImGuiKey`.

**Ex 13.8** For each triangle, find the vertical range of pixel centres. For each row centre `y`, intersect the horizontal line with the two edges that cross it to get `xl` and `xr`, then fill the pixels with centres in `[xl, xr)`, taking the top-left rule into account for ties (`ceil(xl - 0.5)` to `ceil(xr - 0.5)`). Using the integer edge functions to compute `xl` and `xr` exactly keeps the same rounding. The scanline version does less work per pixel (no three edge evaluations) and wins on big triangles. It loses on thin ones, where the setup per row dominates, and anti-aliasing fringes are all thin. Floating point `xl` and `xr` lose the exactness that the integer edge functions give, so shared edges can disagree by a pixel unless you also use fixed point.
